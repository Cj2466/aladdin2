READ THIS BEFORE TRUSTING ANY BEFORE/AFTER NUMBER BELOW.

Companion machine-readable evidence: price_store_pit_2026-09-04.json (every

==========================================================================
0. WHAT CHANGED, IN ONE PARAGRAPH
==========================================================================
YFinanceProvider used to call yf.download(auto_adjust=True) on every price
read, with no persistence. It now asks Yahoo for the vendor's INPUTS
(auto_adjust=False + actions=True), converts them to an as-traded basis,
records them once and never overwrites a recorded row, and computes every
adjusted series itself from that stored copy. This is the DEFAULT for every
caller, not an opt-in. The earlier snapshot-freeze (commit 24f0974) fixed one
family by asking it to opt in, and froze the vendor's DERIVED OUTPUT rather
than its inputs; this replaces it as the general mechanism.

==========================================================================
1. THE BUG, AND THE TWO SEPARATE MECHANISMS BEHIND IT
==========================================================================
An adjusted close is not a fact, it is an opinion about every corporate
action since. Re-asking a vendor for one gives a different answer over time.
Two distinct mechanisms were measured here, and they matter differently:

 (a) CONTINUOUS, EVERY FETCH — float32 quantisation of the adjusted series.
     Two fetches of the SAME 768-name universe over the SAME 2015-01-07..
     2026-08-31 window, 2h04m apart (2026-09-03T23:34Z vs 2026-09-04T01:38Z):

        field              cells      differ >1e-9   differ >1bp   max rel
        auto_adjust Close  1,701,367  952,705 (56%)  0             1.300e-06
        raw Close          1,701,367  0              0             0.000e+00
        raw Open           1,701,367  0              0             0.000e+00
        raw Volume         1,701,368  0              0             0.000e+00
        Dividends          1,701,368  0              0             0.000e+00
        Stock Splits       1,701,368  0              0             0.000e+00

     The adjusted series moved on 56% of cells; every raw input was
     BIT-IDENTICAL. The implied relative precision of the moves has median
     1.229e-07 against a float32 epsilon of 1.19e-07 — i.e. Yahoo serves the
     adjusted close at float32 and re-rounds it non-deterministically per
     fetch, while serving the raw fields at full precision. THIS ANSWERS THE
     "is raw actually more stable" QUESTION EMPIRICALLY AND DECISIVELY: yes,
     strictly, over this window.

 (b) EPISODIC — corporate-action reprocessing. Caught in the act over a
     5h05m gap (t1 2026-09-03T23:34Z vs t3 2026-09-04T04:39Z), same universe,
     same window, zero code changes:

        field              cells      differ >1bp   max rel move   tickers
        auto_adjust Close  1,701,367  29,153 (1.71%)  1.0400e-02   11
        raw Close          1,701,367  0               0.000e+00    0
        Dividends          1,701,368  0               0.000e+00    0
        Stock Splits       1,701,368  0               0.000e+00    0

     Eleven names (BF-B, BR, HD, HRB, LIN, LUV, NE, NEM, PFG, QCOM, VNT) had
     their ENTIRE adjusted history rescaled by up to 1.04% while every raw
     input stayed bit-identical. The only way that happens is that Yahoo
     processed a distribution with an EX-DATE AFTER THE WINDOW'S END, which
     back-adjusts everything before it. That is the mechanism in one
     sentence: THE ADJUSTED SERIES DEPENDS ON EVENTS OUTSIDE THE REQUESTED
     WINDOW; THE RAW SERIES DOES NOT. It is also why the store's adjustment
     base date is the window's last row, per CRSP — an event after `end`
     cannot reach back into it.

     STATED HONESTLY, THIS PARTICULAR EPISODE WAS RETURN-NEUTRAL. Those 11
     rescales were UNIFORM across each ticker's whole history, so daily
     returns were untouched (max return drift 1.912e-06, zero cells >1bp).
     Levels were not — dollar-volume and minimum-price gates read levels.
     The genuinely damaging variant is a rescale whose boundary lands INSIDE
     the window, which manufactures one day's return; that variant was
     measured on 2026-09-04 (DOW, PCL, Q, FCPT — see
     project_lazy_prices_confound) but did not recur in either window
     measured here. So: the large drift is EPISODIC and its return impact
     depends on where the boundary falls. Do not read the numbers above as
     "the old path was corrupting every backtest"; read them as "the old
     path could not promise that it wasn't."

Both mechanisms are eliminated by the same fix, for different reasons: (a)
because the store never reads the adjusted series at all, (b) because a
recorded row is never overwritten and the base date sits inside the window.

==========================================================================
2. ARCHITECTURE, AND WHY IT IS THIS ONE — WITH SOURCES
==========================================================================
CRSP Data Description Guide, Chapter 5 "CRSP Calculations", p.117 (retrieved
2026-09-04 from leiq.bus.umich.edu/docs/crsp_calculations_splits.pdf),
verbatim: "CRSP provides raw, Unadjusted Data, but data utilities stk_print
and ts_print can be used to generate Adjusted Data." "An adjustment base date
is chosen as the anchor date... The adjustment base date is usually the last
available day of trading." "A(t)=P(t)/C(t)" for price and dividend data,
"A(t)=P(t)*C(t)" for share and volume data. p.119: "Total Return = (adjprc +
(divamt / cumfacpr / facpr)) / prev_adjprc - 1".

That is exactly this module's design: store raw, adjust on read, base at the
window's last day, prices divided by the cumulative split factor and volume
multiplied by it.

A CORRECTION TO THE BRIEF THIS WORK STARTED FROM. The preliminary research
cited yfinance issues #2603, #1273 and #687 as documenting the retroactive-
restatement behaviour. They were read in full and they do not. #2603 is a
MISSING split adjustment on an Indian ticker, closed "not planned"; #1273 is
a wrong dividend adjustment of WEEKLY/MONTHLY bars; #687 is a semantics
question about auto_adjust vs back_adjust. All three support "Yahoo's
adjustment is not reliable"; none supports "the series changes under you over
time". The support for THAT claim is (i) this project's own measurements
above and (ii) the yfinance project's own Price-repair wiki page, which
states Yahoo carries "missing dividend adjustments" and "missing split
adjustments" and warns that "If Yahoo eventually does fix the bad data that
required reconstruction, you will see it's slightly different". Separately
relevant: yfinance #2666 reports that Yahoo's Dividends field is the SUM of
dividends and capital-gain distributions for funds, which corrupts Adj Close
— the store therefore records Capital Gains as its own column.

ALTERNATIVES CONSIDERED AND REJECTED: freezing the adjusted series (freezes a
derived opinion; cannot absorb a new trading day without splicing a
differently-based series onto it — the exact artefact being fixed); pinning a
vendor version or as-of query (Yahoo exposes none); switching vendor (every
free feed reachable here serves a continuously-revised adjusted series with
no as-of facility — that changes whose revisions bite, not whether they do).

ONE COMPROMISE YAHOO FORCES. It does not serve a genuinely unadjusted price:
auto_adjust=False's Close for AAPL on 2020-08-28 is 124.8075, not the 499.23
that traded, because it is already split-adjusted onto today's basis. The
store un-split-adjusts on ingest so a stored row is basis-invariant. Verified
against that independently known fact: the reconstruction returns 499.2300.

3. THE ADJUSTMENT CONVENTION — A DECISION LEFT TO A HUMAN
==========================================================================
Two conventions are implemented; they differ only in how a distribution
enters the chained return across its ex-date.

    YAHOO   r(t) = P(t) / (P(t-1) - D(t)) - 1        <- the DEFAULT
    CRSP    r(t) = (P(t) + D(t)) / P(t-1) - 1        <- the correct definition

They agree to O((D/P)^2) — about 3e-05 on a typical 0.5% quarterly dividend,
so for 20,039 of the 20,069 distribution events in this project's universe
the choice is immaterial. They diverge violently on large distributions,
where YAHOO IS SIMPLY WRONG:

    KDP 2018-07-10 (Keurig / Dr Pepper Snapple merger consideration)
      close 123.66 -> 22.19 against a $103.75 distribution
      true total return    (22.19 + 103.75)/123.66 - 1 = +1.84%
      Yahoo's convention   22.19/(123.66 - 103.75) - 1 = +11.45%

Cumulative effect over 2015-2026, CRSP vs YAHOO, per name:
    S&P 500 (611 names)          median +0.0000%, p5 -0.2271%, p95 +0.1436%
      worst: DHR -35.7%, DXC -27.1%, XRX -12.8%, KDP -8.7%, AIV -4.0%
    bonds/commodities/small-cap  median +0.0000%, p5 -0.2588%, p95 +0.2705%
      worst: SITC -7.0%, SSP -4.2%, ELME -3.0%, HCC -2.7%, RPT -1.2%

So the production price path has been carrying materially fabricated
cumulative returns for roughly ten names out of ~1,500. Yahoo additionally
DOUBLE-ENCODES a spin-off as both a split ratio and a distribution on the
same ex-date (exactly 3 such events here: DHR/Fortive 2016-07-05, DXC/CSRA
2015-11-30, XRX/Conduent 2017-01-03); the CRSP path drops the duplicate, the
YAHOO path keeps it for faithfulness.

Impact of switching the default, on the live registrations:
    cbop_ls_h63                  Sharpe +0.00023, DSR +0.00029
    noa_neutral_ls_h126_median   Sharpe -0.00014, DSR -0.00010
    si_ratio_hedged_h21          Sharpe -0.00197, DSR -0.00124
    lazy_jaccard_full_h126_ivol  Sharpe -0.01686, DSR -0.01569   <- largest
    xc_btcbeta_l180_h180         exactly 0 (crypto has no distributions)
No DSR floor is crossed by the switch.

THE DEFAULT IS DELIBERATELY LEFT AT YAHOO, AND THAT IS NOT AN ENDORSEMENT.
It is what makes this change provably numerics-neutral, so that section 4's
before/after isolates the reproducibility fix from a redefinition of what a
return is. Flipping it would change every recorded number in the project at
once. That is a decision for a human. RECOMMENDATION: flip it, in its own
reviewed change, because knowingly retaining a formula that reports +11.45%
for a day that returned +1.84% is not defensible — but not as a side effect
of an infrastructure commit.

everything ever fetched per ticker, rather than whichever single fetch a
caller happens to read.

8. KNOWN LIMITATIONS, STATED RATHER THAN SMOOTHED
==========================================================================
 * PriceBar (price_cache.py) still caches a DERIVED value — an adjusted close
   whose meaning depends on a base date it does not record — so two rows
   written by different calls can sit on different bases and a read spanning
   both splices them. Pre-existing, same magnitude as before (order 0.3%),
   and left unfixed on purpose: PriceBar is read directly by
   execution_runner and reached through 43 call sites. Every cross-sectional
   family calls the provider directly and never touches it; the exposure is
   the portfolio/risk API path. Recorded in that module's docstring.
 * Production (Render free plan, no persistent disk) has an EPHEMERAL
   backend/data, so the store starts empty after every deploy and hibernate.
   Harmless — a live tick wants a fresh fetch and writes its durable output
   to Postgres — but it means the reproducibility benefit is a local-research
   benefit. Store writes degrade to a logged warning so an unwritable disk
   can never fail a live tick.
 * A first fetch that captures a transient vendor glitch freezes it. Mitigated
   by an ingest plausibility gate, by logging every held-back revision at
   WARNING, and by resync_ticker as the explicit, never-automatic escape.
 * The store is gitignored (~120MB at full scale). Unlike the other vendor
   caches it is not simply refetchable: a rebuild re-asks Yahoo and Yahoo's
   answer for an already-stored date may have changed. Evidence that this
   costs little in practice: merging four independently-fetched snapshots
   that overlapped on already-stored tickers produced ZERO revisions.
