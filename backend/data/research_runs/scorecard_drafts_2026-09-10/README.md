# Scorecard drafts, 2026-09-10 — mechanical fields only, NOT final scorecards

## What these are

`tests/test_registration_scorecards.py::test_every_family_has_a_scorecard` is
deliberately red: as of this commit, 55 of 57 families with persisted trial
results or a live forward registration have no committed registration
scorecard under `data/research_runs/scorecards/`. That test's own module
docstring forbids closing the gap by writing scorecards from the code:

> "An honest Layer 2 source_locus needs the construction context the
> original author had — which paper section they were reading when they
> picked a breakpoint — and inventing one produces a citation that LOOKS
> verified and is not."

The four files in this directory (`<family_key>_SCORECARD_DRAFT.json`, one
per family holding a live forward registration: `quality_cbop`,
`short_interest_ratio`, `lazy_prices_jaccard_full`, `cross_sectional_crypto`)
are **not** an attempt to satisfy that test. They were generated by
`build_scorecard_drafts.py`, which pulls only what can be read mechanically
from persisted records — the DB (`cross_sectional_trial_results`), the
committed DSR ladder (`app/services/research_lab/dsr_policy_n.json`), each
family's own `*_forward_registration.py` module, and (where one exists) a
committed `*_PREREGISTRATION.txt`.

## What is filled

For each family: `family_key`, `covers_family_keys` (the live-registration
key and the distinct trial-results key it maps to, where they differ —
see `registration_scorecard.py`'s note on the two family-key namespaces),
`pattern_id`, `written_at`, `author`, and inside `layer_1_statistical`:
`best_spec_pattern_id`, `n_local`, `dsr_pass_threshold` (three of four; see
below), `dsr_by_n` at `n_local` and the three pooled ladder rungs
(43, 397, 1131), `sharpe_net_annualized`, `n_observations`, and
`preservation_score` / `preservation_score_no_stab` (three of four).

The pooled-rung DSR values are **not** persisted anywhere — they were
computed by calling the same two certified functions
`deflated_sharpe.compute_deflated_sharpe` itself calls
(`expected_max_sharpe_under_noise`, `probabilistic_sharpe_ratio`) directly
against each family's already-persisted summary statistics (skewness,
kurtosis, sigma_SR, sharpe, n_observations), with `n_trials` swapped for
each rung. This is the same technique already used on a real, merged
scorecard — see `data/research_runs/scorecards/low_frequency_patterns_SCORECARD.json`'s
`layer_1_statistical.ladder_note_2026-09-09`. Every recomputed value was
checked to reproduce the family's own persisted DSR at `n_local` to within
1e-9 before being trusted for the other rungs; the script raises rather than
proceeding silently if that check fails.

## What is missing, and why (see each draft's own `gaps` array for detail)

* **`decision`, `decision_rationale`** — operational judgments, not
  mechanical facts.
* **`verdict`** — left `null` in every draft even though it is
  deterministically computable from `dsr_by_n` and `dsr_pass_threshold`
  (Policy D's `policy_d_verdict()`). The computed value is recorded in a
  non-schema reference field (`verdict_computed_for_reference_only_NOT_A_SCHEMA_FIELD`)
  for a human reviewer to see, but is never copied into `verdict` itself —
  that copy is a human decision, not this script's.
* **The entire `layer_2_mechanism_fidelity` block** — every field requires
  reading the actual source paper(s). This is the block the test's own
  docstring is protecting; nothing here was reconstructed from code.
* **`layer_3_regime_conditional`'s `source_claim_type` / `claim_evidence`** —
  requires reading the source literature to determine whether its claim is
  unconditional or regime-conditional.
* **The entire `layer_4_economics` block** — cost-scenario sourcing,
  capacity method, and the regime-coverage narrative all require judgment.
* **`layer_1_statistical.power`** — left `null` for all four families. The
  power block must be seeded from the claimed Sharpe the *pre-registration*
  stated before the family ran; only two of the four families
  (`short_interest_ratio`, `lazy_prices_jaccard_full`) even have a committed
  `*_PREREGISTRATION.txt`, and picking out "the" claimed Sharpe and
  converting it net-of-costs the way the source paper intended is an
  interpretive task, not a lookup.
* **`preregistration_path`** — filled for two families
  (`short_interest_ratio`, `lazy_prices_jaccard_full`) where a real
  `*_PREREGISTRATION.txt` was found on disk. For the other two
  (`quality_cbop`, `cross_sectional_crypto`) no such file exists; this is
  stated explicitly in the draft's `gaps` array rather than guessed at or
  left silently blank.
* **`cross_sectional_crypto`'s `dsr_pass_threshold`** — unlike the other
  three families, `bab_forward_registration.py` never pins a single numeric
  bar for this registration (it is an explicit, disclosed exception:
  forward-tracked despite failing this project's normal DSR bars, because
  its backward confound-check passed). Inventing a number here would
  misrepresent what was actually pre-declared, so it is left `null` with the
  reasoning recorded in the draft's `gaps` array.
* **`cross_sectional_crypto`'s `preservation_score`** — the one committed
  preservation-score run (`data/research_runs/preservation_score_2026-09-03.json`)
  predates this family's live registration (wired 2026-09-04) and does not
  cover it. Not recomputed here: recomputing would mean re-running a
  backtest, which the task that produced this directory explicitly forbids.

## Why these are NOT in `data/research_runs/scorecards/`

That directory is read by `registration_scorecard.covered_family_keys()` and
therefore by the completeness test. Putting an incomplete card there would
either (a) fail to parse (the validator rejects any string field matching a
placeholder pattern, and several fields here are `null` rather than a typed
value the schema expects) or, worse, (b) silently satisfy the completeness
check while asserting nothing about Layer 2 — exactly the failure mode
`test_registration_scorecards.py`'s docstring warns against. These drafts
live in their own dated directory so that gap stays visible and honest.

## What happens next

A human (or a Fable-5.1 pass, per this project's model policy for
methodological/adversarial work) reads the actual source papers for each
family, fills Layer 2 and the remaining judgment fields, decides
`dsr_pass_threshold` for `cross_sectional_crypto`, decides `decision` /
`decision_rationale` / `verdict`, and only then commits the result to
`data/research_runs/scorecards/<family_key>_SCORECARD.json` where the
validator and the completeness test will actually see it.
