==============================================================================
THE MEASURED BORROW RATES ARE ADOPTED FOR lazy_prices AND short_interest_ratio
2026-09-06. Two live forward-validation registrations end here, on purpose.
==============================================================================

WHAT THIS IS, IN ONE PARAGRAPH
------------------------------------------------------------------------------
Two LIVE forward-validation registrations were charging 0.0 for short borrow.
Both families' real borrow costs were MEASURED on 2026-09-05 and persisted;
neither was adopted then, because financing_bps_per_year is one of
config_identity()'s six fields, so adopting any rate re-hashes
config_fingerprint and the forward runner's drift gate parks the row as
"spec_drift" -- an operational-status change, and the repo owner's decision.
The repo owner has now made that decision. This run adopts both measured
rates. Nothing else about either family changed.


THE AUTHORIZATION, QUOTED RATHER THAN PARAPHRASED
------------------------------------------------------------------------------
Asked whether to adopt the real borrow rates, and told in the same sentence
that doing so auto-parks the registrations, the repo owner answered:

    "รับ borrow rate จริงของ lazy_prices/short_interest_ratio ไหม
     (จะ auto-park registration) ทำเลย"

    -- "Adopt the real borrow rate for lazy_prices / short_interest_ratio?
        (it will auto-park the registration) -- do it."

That is fully-informed sign-off for the consequence described, and satisfies
CLAUDE.md rule 6 ("never change a live registration's operational status
without the project owner's explicit sign-off"). It authorizes THIS park and
nothing else: no other registration's status was touched, considered, or
allowed to move as a side effect (measured, section 5).

WHY BOTH ARE HALF THEIR MEASURED SHORT-LEG RATE, stated because getting this
backwards would double or halve the charge. financing_bps_per_year charges
GROSS notional held, and both books carry gross ~2x their short notional, so
half the short-leg rate on gross 2.0 is exactly the stated rate on the 1.0
short leg. That is borrow_cost.financing_bps_for_long_short_book, and both
source runs assert the collapse holds for the book they measured rather than
assuming it (the hedged book's implied financing minus B/2 = -1.42e-14).

WHY THE 4-DECIMAL FIGURES AND NOT FULL PRECISION, since the two differ:
  lazy_prices    full precision 48.164359853319304
                 sibling economic run used 48.16435
                 ADOPTED 48.1644
  short_interest full precision 44.77049716292157
                 ADOPTED 44.7705
The three lazy_prices values differ by < 1e-4 bp/yr, i.e. < 1e-8 of notional
per year, which moves no reported digit of any Sharpe or DSR. 48.1644 and
44.7705 are adopted because they are the figures the source runs THEMSELVES
published AND fingerprinted, so the fingerprint each produces is one that was
computed and written down before adoption rather than a new hash nobody has
checked (section 3). Choosing full precision instead would have produced
59c6b6d7... for lazy_prices, which appears nowhere on the record.

SECTION 4: HOW THE STATUS TRANSITION ACTUALLY HAPPENS
------------------------------------------------------------------------------
NO DB ROW'S STATUS WAS WRITTEN BY THIS CHANGE. That is deliberate: forcing a
status column by hand would produce the same end state by a mechanism nobody
could audit, and would be indistinguishable from the mechanism failing.

The real path, read out of the code rather than assumed:

  cross_sectional_forward_validation_runner.py
    _tick()                      -> groups active rows by family
    _process_family()            -> config = adapter.build_config()
                                    cfg_hash_now = config_fingerprint(config)
    _process_registration()      -> DRIFT GATE, before any day is processed:
                                    detect_spec_drift(...) or
                                    detect_config_drift(snapshot,
                                        cfg_hash_now, cfg_now)
                                    if not None: _park_as_drifted(...)
    _park_as_drifted()           -> registration.status = "spec_drift"
  ACTIVE_STATUSES = ("in_progress", "forward_validated")  -- excludes it, so
                                    the row is never loaded again.

So: on the next tick after this lands on a host, each of the two rows is
loaded, its stored fingerprint (2dccbf93…) is compared against the freshly
computed one (97d087f7… / d8f3789e…), the comparison fails, and the runner
parks it itself. The runner is launched in main.py's lifespan and ticks on
settings.forward_validation_check_interval_seconds. There is no manual
per-registration trigger script in this repo and none was invented.

VERIFIED BY EXERCISING THAT PATH, not by reading it:
tests/test_borrow_rate_adoption_parks_registrations.py seeds a real DB row for
each family carrying the REAL registered fingerprints and the REAL spec
fingerprint, hands it to the REAL
CrossSectionalForwardValidationRunner._process_registration with the REAL
adapter's now-adopted config, and asserts the row comes back status
"spec_drift", n_forward_trading_days 0, last_processed_date None, and outside
ACTIVE_STATUSES.

AND VERIFIED ADVERSARIALLY, so a park for the wrong reason cannot read as
success. The same test file re-runs the same row through the same runner with
financing held at the registered 0.0 and everything else live: the gate falls
THROUGH (the row stays "in_progress"), which proves the spec fingerprint and
the other five config fields are unchanged and that financing is the only
thing that moved. Separately, reverting the constant to 0.0 was checked to
turn the park test RED (3 failed), so it is not vacuously green.

SECTION 7: THE LIMITATION ADOPTION DOES NOT REMOVE, LOGGED NOT BURIED
------------------------------------------------------------------------------
1. THE short_interest CONSTANT IS CALIBRATED TO THE REGISTERED SPEC ONLY.
   financing_bps_per_year is a SCALAR on one config shared by all 12 specs.
   The same 2026-09-05 run measured this family's six long_short specs at
   173-215 bp/yr: si_ratio_ls_*'s short leg is the top 5% by short-interest
   ratio and the schedule's expensive tail is the top 10%, so 5% sits wholly
   inside 10% -- tail share exactly 1.0000, book rate exactly 430.00,
   financing exactly 215.0. 44.7705 therefore UNDERCHARGES those six by ~4.8x.
   The constant is set to the REGISTERED book's own rate because that is the
   book with a live forward record. ANY FUTURE READING OF A long_short SPEC'S
   SHARPE OR DSR UNDER THIS CONFIG MUST SUBSTITUTE THE 215.0 ROW. This is
   stated in the constant's own comment, in the family module docstring, in
   the registration file's correction, and in the manifest acknowledgement.

2. IT IS STILL NOT A BORROW-RATE FEED. Every rate here is D'Avolio's or
   Beneish/Lee/Nichols', mapped onto names by a short-interest proxy both
   papers explicitly warn against (D'Avolio p.285). The paid-feed gap stays
   OPEN -- PENDING_PAID_DATA_DECISIONS.md entry P1. These are better
   approximations than 0, 34 or 430; they are not what a broker would charge.

3. THE SCHEDULE OVERCHARGES BY CONSTRUCTION (Beneish/Lee/Nichols p.17: "even
   in the highest SIR decile, less than 30 percent of the stocks are
   special"), percentiles are taken within the S&P 500 cross-section rather
   than market-wide, and borrow_cost.py's samples end 2013. All three point
   the same way: toward OVERcharging, which is the safe direction.

4. lazy_prices HAS 7 OF 24 FORMATIONS UNMEASURED (2015-01 .. 2018-01, before
   FINRA's free file starts). The 17 measured are stable, so extrapolating is
   reasonable -- but it is extrapolation. short_interest's window opens
   2018-01-12 and is near-fully covered.
