1. CME SPAN SETTLEMENTS (cme_span_settlements.py) -- REAL DATA VERIFICATION
----------------------------------------------------------------------------------------------------
  Downloaded 3 real archive files live from ftp://ftp.cmegroup.com/span/archive/cme/ (all
  succeeded, ~11-13 MB zips, ~86-98 MB decompressed text, ~692k-788k lines each):
    - cme.20190102.s.pa2.zip (2019, used by the module's own test fixtures -- chosen specifically
      to check whether the test fixtures were copied from the real file or invented)
    - cme.20200420.s.pa2.zip (2020, the day of the -37.63 WTI negative settlement)
    - cme.20240102.s.pa2.zip (2024)

  FIXTURE-AUTHENTICITY CHECK: grepped the real 2019-01-02 file for the CME ES product/expiration/
  settlement records and found tests/test_cme_span_settlements.py's synthetic P_ES/B_ES/R81_ES/
  R82_ES strings are byte-for-byte IDENTICAL to the real file's lines for the same instrument
  (verified: `grep "^P CMEES" cme.20190102.s.pa2.txt`, `grep "^82CMEES.*201903"`, etc. against the
  test file's literals). The synthetic fixtures were copied from a real file, not invented from
  memory or guessed at.

  DECODE VERIFICATION AGAINST REAL FILES: ran the module's own parse_pa2_zip() against all 3 real
  files (865, 857, and 925 rows respectively, all 31 universe roots present in every file) and
  hand-inspected the decoded output:
    - ES 2019-01-02 front contract (201903) settle 2511.00 -- matches the test's cited Yahoo
      ES=F close.
    - CL May-2020 (contract_month 202005) on 2020-04-20: settle -37.63, decoded from raw field
      "0003763" with sign byte "-". This is the real, famous WTI negative-settlement event
      (widely documented; the raw "82" record itself, grepped directly from the real file, reads
      "...000000000003763-+10000+C"). Independently confirms both the settlement decode AND the
      sign-byte handling on the single highest-stakes real-world value in this dataset.
    - CL front contract on 2019-01-02: the module correctly identifies 201902 (Feb-19, expiration
      20190122) as the first unexpired contract (201812 and 201901 had already expired by that
      date, exp 20181119 and 20181219) -- settle 46.54.
    - ZN (10Y note, alignment "C", 32nds-with-quarter-code) on 2020-04-20: raw "0139035" ->
      139 + (3 + 0.5)/32 = 139.109375, consistent with a flight-to-quality rally level.
    - ZC (corn, alignment "0", cents-with-quarter-code) on 2024-01-02: raw "0004637" -> 463.75
      cents ($4.6375/bu), consistent with real 2024 corn levels.
    - NG on 2024-01-02: 2.619 $/MMBtu, consistent with real 2023-24 natural gas levels.
  None of these were assumed correct from the docstring's own claims -- each was recomputed by
  hand from the raw byte fields and cross-checked against independently known market levels or
  (for CL) an independent live source (below).

  INDEPENDENT CROSS-CHECK AGAINST A FRESH LIVE EIA FETCH (not the prior session's cached numbers):
  fetched https://www.eia.gov/dnav/pet/hist/RCLC1d.htm live in this session (not reused from
  phase 1) and parsed it with the module's own eia_nymex_futures.parse_weekly_html():
    - EIA RCLC1 on 2020-04-20 (live fetch, this session) = -37.63 -- exact match to SPAN's decoded
      CL May-20 settlement, independently re-derived.
    - EIA RCLC1 on 2019-01-02 (live fetch, this session) = 46.54 -- exact match to SPAN's decoded
      CL Feb-19 (the correctly-identified first-unexpired contract) settlement.
  Both matches were performed by this session against a fresh live fetch, not by trusting either
  prior session's report of the same comparison.

  STRESS TESTS (malformed input, no silent failure anywhere found):
    - Empty bytes to parse_pa2_zip() -> zipfile.BadZipFile (correct: not a valid zip).
    - Valid zip containing an empty .pa2 member -> SpanDecodeError ("first record is not the '0 '
      exchange-complex header") -- correct, not silently returns empty rows.
    - Zip with 2 .pa2 members (ambiguous) -> SpanDecodeError ("expected exactly one .pa2 member").
    - Non-zip garbage bytes -> BadZipFile.
    - decode_settlement() with a short/non-7-digit raw field -> SpanDecodeError.
    - decode_settlement() with a non-digit raw field -> SpanDecodeError.
    - Unknown alignment code, or an out-of-set fraction-code last digit for "C"/"0" -> SpanDecodeError
      (already covered by the pre-existing tests, re-confirmed here).
  No `except: pass` or equivalent silent-swallow pattern exists anywhere in the decode/parse path;
  fetch_archive_zip() retries on transient network errors and only returns None for the documented
  "550 = no file that day" case (weekends/holidays), re-raising after exhausted retries otherwise.

  A REAL FINDING, NOT A BUG BUT A MONITORING GAP: grepped the real 2019-01-02 file for FUT records
  whose regular-settlement field (bytes 111-117) is all zeros and found 12,586 of them across the
  WHOLE file (e.g. CBOT product code "ZMT", an option-adjacent product not in this project's
  31-root universe). decode_settlement("0000000", ...) legitimately returns 0.0 for such a field --
  that is the correct decode of what the exchange actually printed, not a bug -- but 0.0 is
  economically implausible for every instrument this project tracks. Checked specifically: NONE of
  the 12,586 zero-settle rows fall inside GLOBEX_TO_SPAN's 31 target roots on any of the 3 sampled
  files (2019-01-02: 0, 2020-04-20: 0, 2024-01-02: 0). FIXED (a real code change, not just a
  finding): write_manifest() now counts zero_settle_rows per instrument and a
  zero_settle_rows_total, so a future full-archive ingest that DOES hit one inside the target
  universe is visible in the manifest rather than silently accepted as a genuine $0.00 settlement.
  New test: test_manifest_counts_zero_settle_rows_instead_of_silently_accepting_them.

  ROLL/CHAINING LOGIC: none exists in this module (or in databento_futures.py / eia_nymex_futures.py)
  -- the MOP (2012) Section 2.1 chain-building logic lives in data/research_runs/
  run_futures_data_sourcing.py, explicitly out of this audit's stated scope (the three modules
  under audit are ingestion/decode only). So there is no forward-information-leak risk to check
  within the audited files themselves; that check belongs to whichever future task audits the
  chain builder.

  VERDICT: no decode bugs found. One monitoring gap found and fixed (zero-settle tracking). Test
  count for this module: 30 -> 31 (30 original + 1 new).

3. DATABENTO FUTURES (databento_futures.py) -- REAL BUG FOUND AND FIXED
----------------------------------------------------------------------------------------------------
  build_plans() requested GLBX.MDP3 (the 31 CME/CBOT/NYMEX/COMEX roots) from GLBX_START
  (2010-06-06) through `end` for ALL 31 roots -- i.e. it would have re-pulled, and re-billed
  Databento credit for, the entire 2013-01-02..2025-09-12 window that CME SPAN already covers for
  free. This directly contradicts this phase's explicit scope ("do not re-pull what's already
  free") and would have been a real, avoidable waste of the $125 credit on the very first live run
  had it shipped unaudited.

  FIXED: added CME_BRIDGE_START, derived (not re-typed) from
  cme_span_settlements.SPAN_ARCHIVE_LAST_DATE + 1 day (2025-09-13), so the two modules cannot
  silently drift apart on the boundary date if SPAN_ARCHIVE_LAST_DATE is ever updated. build_plans()
  now requests GLBX.MDP3 ONLY for [CME_BRIDGE_START, end], with a ValueError guard if `end` is
  called before the bridge window starts (i.e. before there is anything new for Databento to
  supply). IFUS.IMPACT (KC/SB/CT) is unchanged: full available history from 2018-12-23, since CME
  SPAN never covered ICE-listed products at all.

  This also shrinks the size/cost estimate in the module docstring: the original (mis-scoped)
  GLBX estimate was ~56 MB for 16 years of full history; the corrected bridge-window-only estimate
  is on the order of 1-2 e5 records (roughly a year or less as of 2026-09-07), an order of
  magnitude smaller. Both figures were, and remain, comfortably inside the $125 credit -- the bug
  was about wasted spend and re-pulling already-free data, not about the credit being insufficient.

  REQUEST-SHAPE VERIFICATION AGAINST DOCUMENTED DATABENTO SEMANTICS (all cited in the module's
  existing docstring from phase 1, re-checked here rather than re-trusted): dataset codes
  GLBX.MDP3 / IFUS.IMPACT, schema "ohlcv-1d", stype_in "parent" with symbols formatted as
  "<ROOT>.FUT" (e.g. "ES.FUT", "KC.FUT") per Databento's documented SType.PARENT symbology ("a
  Databento-specific symbology for referring to a group of symbols by one 'parent' symbol, e.g.
  ES.FUT"). CONTINUOUS symbology is deliberately NOT used, matching this project's stated MOP
  Section 2.1 individual-contract chaining approach rather than a front-month splice (the exact
  defect class P4 already rejects Yahoo's `=F` for).

  make_client() correctly refuses (raises RuntimeError) when DATABENTO_API_KEY is unset, before
  any import of the real `databento` package -- confirmed by re-running
  test_make_client_refuses_without_key. The real `databento` package is imported lazily, inside
  make_client() only, so importing this module never requires the dependency to be installed.

  COMPLETED (per Job 2): wrote data/research_runs/fetch_databento_bridge_and_ice.py, the single
  script call the task asked for. It: (1) refuses to run without DATABENTO_API_KEY, before any
  network I/O; (2) requests Databento's own cost estimate first via the documented metadata

  MOCKED/SYNTHETIC TEST COVERAGE (no network, no key, no real `databento` import anywhere in the
  test suite): tests/test_databento_futures.py's existing FakeClient tests were updated for the
