5. CANDIDATE (d): CROSS-STORE DIVERGENCE IN THE "FIRST WRITE WINS" RAW
   PRICE STORE — CONFIRMED, WITH AN EXACT MECHANISM
==========================================================================
Hypothesis: price_store.py section 4's own stated policy ("A (ticker,
date) row, once stored, is NEVER overwritten by a later fetch... A later
fetch that disagrees with a stored row is... COUNTED and SURFACED on
PriceStoreReport.revisions") means reproducibility holds WITHIN one
persistent store but is not guaranteed ACROSS two independently
first-populated ones.

5.1 FIRST PASS, 111 TICKERS — A NEGATIVE RESULT, LATER SHOWN TO BE THE
    WRONG SAMPLE SIZE

A genuinely empty second PriceStore (a separate git worktree,
short-interest-repro-2026-09-04) independently fetched 111 of this
family's universe tickers via get_price_history, several hours after the
main repo checkout's own store had already been populated. Every raw
OHLCV+dividend+split cell on every shared trading day (~192,700 cells) was
compared field-by-field between the two stores' on-disk CSVs: ZERO
differences. This result is left in the record rather than deleted,
because the correct lesson from it is methodological (111 of 597 was not
enough to catch a problem affecting 2 tickers), not "the mechanism is
absent."

5.2 SECOND PASS, THE FULL 597-TICKER SNAPSHOT BUILT FOR THE
    REPRODUCIBILITY FIX (section 6) — CONFIRMED, 2 TICKERS, EXACT
    MECHANISM TRACED

Re-running the same field-by-field diff against the full 597-ticker
snapshot saved for the price_frames fix:

    tickers compared:      597
    tickers with any differing cell:  2  (APH, MNST)
    differing cells: concentrated entirely in adjusted Close; raw
        Open/High/Low/Volume/Dividends matched for both tickers

For APH, ratio of worktree-close/main-close was a UNIFORM 2.0 across every
checked date from 2017-12-13 through 2026-08-31 (spot-checked at 2017-12-13,
both split boundaries, and the final week of the window). For MNST, the
ratio was 2.0 before 2026-08-11 and exactly 1.0 on and after — i.e. lines
up precisely with a real split ex-date already present in BOTH stores'
split columns.

TRACED TO SOURCE. Both tickers had a genuine, real 2-for-1 stock split
within days of this investigation:

    MNST   split ex-date 2026-08-11  (present in both stores' split column)
    APH    split ex-date 2026-09-03  (yfinance Ticker("APH").get_info()
                                       lastSplitDate = 1788393600 ->
                                       2026-09-03 UTC; ONE CALENDAR DAY
                                       before this investigation ran)

price_store.cumulative_split_factor, called directly against each
ticker's OWN currently-stored, currently-complete split column, returns
the mathematically correct factor:

    MNST cumulative_split_factor at 2017-12-13, using the main store's own
    6-event split column (2005, 2006, 2012, 2016, 2023, 2026-08-11) = 4.0

    A fresh, independent yfinance Ticker("MNST").history() query gives
    Close(2017-12-13, auto_adjust=False) = 15.8774995803833 with splits
    {2023-03-28: 2.0, 2026-08-11: 2.0} — 15.8774995803833 x 4.0 =
    63.50999832153... matching the WORKTREE'S stored raw close
    (63.5099983215332) to every printed digit.

    The MAIN REPO'S OWN stored value for the same cell is 127.0199966430664
    — exactly 2x the correct value, i.e. missing exactly one of the two
    post-2017 split factors.

MECHANISM: the main repo's row for MNST/2017-12-13 was written by an
EARLIER fetch/merge, before the 2026-08-11 split had propagated into every
code path this project's ingestion touches. PriceStore.merge_ticker
DISCARDS an incoming row for a date already present (first-write-wins,
section 4) rather than adopting the new, correct value — the split
subsequently became known and its OWN new row (2026-08-11 itself) was
correctly appended, but every PRE-EXISTING row before it was never
revisited or rescaled.

WHY THIS IS PERMANENT, NOT MERELY STALE-UNTIL-THE-NEXT-FETCH:
yfinance_provider.py's own coverage-ledger docstring states a rolling
window (end >= today) is "refetched once per calendar day" — but this
family's window ends 2026-09-01, which is BEFORE "today" (2026-09-04), so
that daily-refresh rule never applies to it. The coverage ledger
(data/price_store/v1/_coverage.json) already records APH and MNST as
covered through 2026-09-02 — verified directly by reading the ledger file.
Any future call for this exact (tickers, window) combination will be
served straight from the store, is_covered() will return True, and
_download_raw_with_actions will never run — meaning
PriceStoreReport.revisions, the store's own disclosed safety net for a
disagreeing re-fetch, can never fire for this cell, because it only
triggers on an ACTUAL re-fetch attempt, which the coverage ledger's entire
purpose is to avoid.

VERDICT: CONFIRMED, with an exact, independently-verified mechanism — not
a hypothesis. This is a REAL, PROJECT-WIDE ARCHITECTURAL GAP in
price_store.py, not a short_interest-specific one: any family holding a
ticker that splits AFTER that ticker's row is first written to the store
will silently carry a stale, pre-split-basis price for its entire earlier
history, for as long as the store persists, with no automatic repair
(PriceStore.resync_ticker is the correct, existing, but never
automatically-invoked remedy). Currently bounded to local development
only — Render's free tier has no persistent disk, so production's store
is rebuilt fresh on every deploy (price_store.py's own disclosed
operational limitation) — but this would become a live-registration risk
the day this project gets persistent production storage. NOT FIXED IN
THIS TASK, deliberately: it is a bigger, separate, more consequential
change touching every live registration's price data, and this project's
own standing practice is to disclose such a gap precisely and scope it out
rather than bundle an unreviewed architectural change into an unrelated
task (the same discipline already applied to the lower-priority
universe/membership live-fetch gap).

6. WHAT THIS LEAVES, AND THE FIX MADE
==========================================================================
(a) is refuted. (b) and (c) are real but measured immaterial to this
window. (d) is CONFIRMED, with an exact, traced mechanism: a real stock
split (APH, ex-date 2026-09-03 — one day before this investigation ran)
executing in the middle of this exact investigation's own real-time
window, colliding with this project's first-write-wins store never
revisiting an already-written row. This plausibly explains the specific
+0.41611 -> +0.42004 movement between this investigation's own two runs
(the CRSP-convention default-provider run in section 1, and the
snapshot-pinned run below) — but it was found too late in the window's own
real-time journey to test against the ORIGINAL four historical
measurements (+0.4531 / +0.41870 / +0.42712 / +0.42516), whose
per-worktree caches no longer exist to re-inspect. It is recorded as the
CONFIRMED MECHANISM CLASS behind this family's reproducibility problem,
not a retroactive line-by-line explanation of every one of the four
numbers.

THE FIX MADE, regardless of whether this exact APH/MNST event is what
drove any one of the four original numbers: run_short_interest_screening
gained a `price_frames` parameter, structurally identical to
run_lazy_prices_screening's own (added the same night, same reason — see
lazy_prices_forward_registration.py's 2026-09-04 correction). Passing a
saved snapshot (yfinance_provider.save_ohlcv_snapshot /
load_ohlcv_snapshot) replays a FROZEN price panel instead of triggering a
live fetch — sidestepping candidate (d) entirely for this family's own
backward-research purposes, regardless of whether the deeper price_store
fix is ever built.

PROOF: one snapshot was saved for this exact window (691-name point-in-time
universe, 94 tickers unresolved — identical to the live-fetch run's own
missing-ticker count, confirming the snapshot captures the same coverage),
then replayed through two independent process invocations:

    RUN 2 (snapshot replay): si_ratio_hedged_h21 sharpe=0.4200421089865406
                              dsr=0.7745798160040326

8. NEW OPEN ITEM SURFACED, NOT FIXED HERE
==========================================================================
price_store.py's "first write wins" policy has no mechanism to detect or
repair a row whose raw reconstruction becomes stale because a ticker
SUBSEQUENTLY splits after that row was first stored, when the affected
query window is entirely in the past (so the coverage ledger's rolling-
window daily-refresh rule never revisits it). This is project-wide, not
short_interest-specific, and currently bounded to local development only
(production's store has no persistent disk yet). Recorded here for
whoever next touches price_store.py or reviews the live registrations'
price-data reliability; not chased further in this task.
