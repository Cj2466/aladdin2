This file follows the convention a3ba0bc (the CRSP dividend convention) and
77e77d7..61bd307 (the price-store rewrite) established for a change that moves
a live registration's numbers: state the date the calculation changed, state
both methods, measure the delta on one shared data build, and DO NOT rewrite
anything already persisted under the old method.

WHAT CHANGED
------------------------------------------------------------------------------
  BEFORE 2026-09-05   cost_model="edge_spread" priced off
                      spread_estimator.build_edge_half_spread_frame
  FROM   2026-09-05   priced off build_calibrated_half_spread_frame, via the
                      family's own cross_sectional_lazy_prices.
                      build_lazy_prices_half_spread_frame

Both the backward path (run_lazy_prices_screening) and the live forward tick
(cross_sectional_forward_registry.build_lazy_prices_live_panel) moved together,
and they now share ONE function so they cannot drift apart. Commit 684af61.

WHY. The raw frame's pooled median one-way half-spread on this family's own
real panel is 24.41bp — a 48.8bp full spread on S&P 500 large caps, against
Hagstromer (JFE 2021) Table 1's measured 2.53bp S&P 500 median. ~19x. Two
separable, independently sourced defects, both documented in full in
spread_estimator.py's own section header and in
edge_cost_correction_2026-09-05.txt: bidask's abs() fold instead of the source
paper's truncation (40.4% of cells), and a LEVEL the source paper itself says
cannot be recovered from daily bars for post-2005 large caps. The calibrated
frame keeps EDGE's ranking, pins the level with one pooled scalar to published
spread statistics, and applies an exact per-cell tick floor.

INDEPENDENT RE-DERIVATION
------------------------------------------------------------------------------
Three separate checks, not one.

 1. The four-scenario comparison behind the BEFORE numbers (39f7cb5's
    run_edge_cost_correction_lazy_prices.py, unmodified) was re-run end to end
    on a later day. Every one of its 20 reported figures — 4 Sharpes, 12 DSRs,
    4 cost drags, and the 29/36/36/36/36/0/36 positive-spec counts —
    reproduced exactly.
 2. Every DSR was then re-derived OUTSIDE the pipeline: deflated_sharpe not
    imported, both formulas typed fresh from that module's own source
    equations (SR0 = sigma_SR[(1-gamma)z(1-1/N) + gamma z(1-1/(Ne))]; PSR =
    Phi((SR-SR0)sqrt(n-1)/sqrt(1 - skew*SR + (kurt-1)SR^2/4))), and every
    input taken as a PRIMITIVE off the persisted cross_sectional_trial_results
    rows — never a row's own stored DSR. All 12 agree with the reported table
    to <5e-5, and each hand-derived DSR at N=36 reproduces the persisted dsr
    field to <1e-12.
 3. The AFTER arm above was produced by calling the family's own
    build_lazy_prices_half_spread_frame — the exact function the live tick now
    calls, not the standalone research script's inline builder — and it
    reproduces the earlier calibrated-scenario figures to every digit reported.

The financing accrual was also checked for linearity as an arithmetic control:
drag 0.0396 at 17.0 bps/yr, 0.1122 at 48.1644, 0.5007 at 215.0 — ratios
2.833 and 12.647 against rate ratios 2.833 and 12.647.

WHAT WAS *NOT* CHANGED, AND WHY — financing_bps_per_year STAYS 0.0
------------------------------------------------------------------------------
This is the known-wrong assumption the switch does NOT fix, and it is not
defended here as a right one.

It is unchanged because it is the one cost input that is in config_identity().
Any non-zero value re-hashes config_fingerprint; detect_config_drift then
returns a reason; the runner calls _park_as_drifted; status becomes
"spec_drift", which ACTIVE_STATUSES excludes, permanently and non-reversibly
without a human. Measured directly rather than reasoned about:

    financing 0.0   (registered)  config_fingerprint 2dccbf93...  MATCHES the live row
    financing 17.0  (S2, all GC)                     e63f283c...  -> parks
    financing 48.16 (MEASURED)                       97d087f7...  -> parks
    financing 215.0 (S3, all HTB)                    f56f3176...  -> parks

Adopting any borrow rate therefore ENDS this registration's forward record.
That is an operational-status change, which is the repo owner's decision and
not something a cost fix takes as a side effect. Pinned as an executable
argument in tests/test_lazy_prices_cost_basis_switch.py::
test_any_non_zero_borrow_rate_would_park_this_registration.

THE HONEST READING OF THAT MIDDLE COLUMN, because it is the number that
actually matters and it is not the flattering one. At the measured borrow rate
the family does NOT collapse — 29 of 36 specs stay positive and the registered
spec keeps Sharpe +0.525, nothing like S3's 0/36 — but the registered spec

currently clears. That is exactly the kind of thing a live registration should
be judged on, and exactly why the decision belongs to the repo owner.

NOTHING PERSISTED UNDER THE OLD METHOD WAS REWRITTEN
------------------------------------------------------------------------------
Deliberately, and following the same convention the dividend-convention and
price-store corrections used.

 * The live row's own accumulated forward record is untouched. Its
   day_results_json, formations_json, carry_state_json, n_forward_trading_days,
   n_formations, started_at, min_trading_days_threshold and status are all
   exactly as they were; this change writes to no registration table at all.
   As of this commit the row shows n_forward_trading_days = 0 and
   last_processed_date = NULL in the local database, so locally there is no
   accumulated series for the switch to contaminate — but that is a fact about
   the local database, NOT about production, and the change is made as though
   there were a record to protect, because on the deployed host there may be.
   THE CONSEQUENCE FOR ANY ROWS THAT DO EXIST, STATED RATHER THAN GLOSSED: days
   realized before this commit were priced on the raw frame and days realized
   after it are priced on the calibrated one, so a forward series that spans
   this date is a SPLICE, and its cost basis changes at this date. That is the
   whole reason this file exists and is dated.
 * Every persisted backward run keeps its own numbers. run tags
   lazy_prices_2026-09-01, edge_cost_correction_2026-09-05_*,
   lazy_prices_ptit_fix_verification_*, and every other historical row in
   cross_sectional_trial_results are left exactly as computed. None is
   recomputed, corrected in place, or deleted.
 * build_edge_half_spread_frame itself is still byte-identical and is still
   exported. Every historical run under cost_model="edge_spread" therefore
   stays exactly reproducible by calling it directly — which is what the
   BEFORE arm above does.
 * The three arms of this run are persisted as NEW rows under new run tags
   (cost_basis_switch_2026-09-05_before_raw_edge / _after_calibrated /
   _after_calibrated_measured_borrow), never as edits to old ones.
 * lazy_prices_forward_registration.py carries a dated CORRECTION section for
   this change, appended, with nothing above it rewritten — the same
   pure-append convention its three previous corrections used.
